# ableops-kafka-mcp 서비스 구축 초기요청

너는 Go 기반 MCP 서버를 개발하는 시니어 백엔드 엔지니어다. 아래 요구사항에 따라 별도 프로젝트를 초기 구성하고, 실행 가능한 조회 전용 MCP MVP까지 구현하라. 계획만 제시하지 말고 코드·설정 예제·테스트·문서를 완성하라.

## 1. 작업 환경과 목표

* 기존 서비스 소스: `D:\golang\go-workspace\kadmin`
* 신규 프로젝트 경로: `D:\golang\go-workspace\ableops-kafka-mcp`
* 프로젝트명: `ableops-kafka-mcp`
* Go 모듈: `github.com/heartblast/ableops-kafka-mcp`
* 기존 서비스 원격 저장소: https://github.com/heartblast/ableops-kafka
* 공식 MCP Go SDK: https://github.com/modelcontextprotocol/go-sdk
* 기본 개발 환경: Windows / PowerShell

기존 ableops-kafka REST API를 호출하는 독립 MCP 서버를 만든다. 향후 내부 LLM 기반 채팅 서비스와 AI 클라이언트에서 Kafka 운영 현황을 조회하고 변경을 신청할 수 있도록 한다.

**이번 구현 범위는 프로젝트 기반 구성과 조회 전용 MCP 도구다.** 채팅 UI, LLM 호출, 변경 신청·승인·반영, 공용 HTTP 서비스는 후속 범위로 둔다.

## 2. 작업 경계

* 기존 `kadmin` 디렉터리는 분석·참조 대상으로만 사용한다.
* 기존 소스·설정·Git 작업 상태를 변경하지 않는다.
* 기존 저장소에서 checkout, reset, clean, pull 등을 수행하지 않는다.
* 기존 서비스 실행, DB 마이그레이션, 운영 Kafka 접속은 수행하지 않는다.
* 기존 설정 파일의 토큰·비밀번호·인증서 개인키를 출력하거나 신규 프로젝트에 복사하지 않는다.
* 신규 경로가 이미 존재하면 파일과 Git 상태를 먼저 확인하고 사용자 작업을 보존한다.
* 신규 경로가 없으면 생성한다.
* 원격 저장소 생성·push·배포는 수행하지 않는다.

WSL 등 다른 실행 환경이면 실제 접근 가능한 경로를 확인해 대응 경로를 사용한다. 로컬 경로에 접근할 수 없으면 접근한 것처럼 진행하지 말고 제약을 명시한다. 원격 소스를 사용하면 로컬 소스와의 차이를 확인하지 못했다는 사실을 기록한다.

## 3. 사전 분석

작업 위치에 적용되는 AGENTS.md·CLAUDE.md 등 지침과 설치된 Go·Git 환경을 확인한다.

**API 계약은 로컬 `kadmin` 소스를 우선 기준으로 분석한다.** 다음 정보를 기록하라.

* 현재 브랜치와 HEAD SHA
* 관련 파일의 미커밋 변경 유무
* 실제 분석에 사용한 파일 경로
* 로컬 작업본 기준이라는 사실

원격 최신 코드로 임의 변경하거나, 로컬 소스와 원격 문서를 혼합해 하나의 계약으로 취급하지 않는다.

다음 경로를 우선 확인하되 현재 구조가 다르면 실제 구현을 찾아라.

* `go.mod`
* `internal/server/routes_cluster.go`
* `internal/server/routes_topic.go`
* `internal/server/routes_event.go`
* 해당 라우트의 실제 핸들러와 응답 DTO
* `internal/middleware/middleware.go`
* `internal/auth/session.go`
* `internal/clusters/rbac.go`
* 관련 API 계약 문서와 테스트

확인 사항:

1. 정확한 API 경로·메서드·입력·응답 JSON 구조
2. Bearer 인증과 토큰 만료·무효화 처리
3. 클러스터별 접근 권한 검사
4. HTTP 상태와 응답 본문의 업무 상태
5. 목록 필터·정렬·페이지 처리 지원 여부
6. 실시간 Kafka 조회와 DB 스냅샷의 구분
7. 부분 실패·기능 비활성·데이터 없음의 표현

문서와 코드가 다르면 실제 핸들러와 테스트를 근거로 계약을 정리한다. 경로·필드·필터를 추측하지 않는다.

## 4. 아키텍처와 의존성

연결 구조:

MCP Client → MCP Server → AbleOps REST Client → 기존 Backend

* 별도 Go 프로세스로 실행한다.
* Kafka·DB에 직접 접근하지 않는다.
* 기존 프로젝트의 `internal` 패키지를 import하지 않는다.
* 로컬 `replace`나 `go.work`로 기존 프로젝트에 결합하지 않는다.
* 기존 서비스의 권한·정책·Lag 판정 로직을 복제하지 않는다.
* 필요한 REST DTO만 신규 프로젝트에서 정의하고 계약 근거를 기록한다.
* MCP 계층과 REST Client 계층을 분리한다.
* 공식 MCP Go SDK의 안정 릴리스와 Go 요구 버전을 확인하고 의존성을 고정한다.
* 기존 프로젝트의 Go 버전을 무조건 복사하지 않는다.
* 불필요한 프레임워크·범용 확장 구조·과도한 인터페이스를 도입하지 않는다.

권장 구조:

* `cmd/ableops-kafka-mcp/`: 실행 진입점
* `internal/config/`: 설정 로딩·검증
* `internal/ableops/`: REST Client·DTO·오류 변환
* `internal/mcpserver/`: 서버 생성·도구 등록·전송 초기화
* `internal/tools/`: 업무별 조회 도구
* `docs/`: 아키텍처·API 매핑·후속 계획
* `scripts/`: PowerShell 실행·검증 스크립트

역할이 명확하면 더 단순하게 조정해도 된다.

## 5. 전송 방식과 인증

이번에는 **개인 사용자용 stdio 전송**을 완성한다.

* 프로세스 하나는 사용자 하나의 AbleOps API 세션 토큰만 사용한다.
* 토큰은 환경변수로 주입한다.
* 토큰을 도구 인자·MCP 응답·로그에 노출하지 않는다.
* 사용자 비밀번호 저장·자동 로그인·관리자 공용 계정은 구현하지 않는다.
* 세션 만료 시 재인증 필요 오류를 반환한다.
* stdout은 MCP 프로토콜 전용, 로그는 stderr 전용으로 사용한다.
* 종료 시 context 취소와 정상 종료를 처리한다.
* 도구 등록과 전송 초기화를 분리해 향후 Streamable HTTP를 추가할 수 있게 한다.

설정 항목:

* `ABLEOPS_BASE_URL`
* `ABLEOPS_API_TOKEN`
* `ABLEOPS_REQUEST_TIMEOUT`
* `ABLEOPS_CA_FILE`
* `MCP_LOG_LEVEL`

필수값·URL·timeout 범위를 시작 시 검증한다. BASE_URL에 `/api`를 포함하는지 규칙을 하나로 정하고 문서와 코드에서 일치시킨다.

기본 HTTPS를 사용하고 개발용 HTTP는 명시적으로 허용한 loopback 대상에 한정한다. 사설 CA를 지원하되 TLS 검증 비활성화 옵션은 만들지 않는다.

리다이렉트로 토큰이 다른 호스트에 전달되지 않게 통제한다. 임의 URL·HTTP 메서드·헤더·API 경로를 받는 범용 요청 도구는 만들지 않는다.

현재 Backend 세션 토큰과 MCP OAuth 토큰을 동일한 것으로 취급하지 않는다. 공용 HTTP 전환 시 필요한 OAuth 인증·사용자 위임·백엔드용 토큰 검증 또는 교환은 후속 설계로 기록한다.

## 6. 조회 도구

실제 로컬 API 계약을 확인한 후 다음 여섯 개 도구를 구현한다.

| 도구                       | 기능                            |
| ------------------------ | ----------------------------- |
| `list_clusters`          | 사용자가 접근 가능한 클러스터 조회           |
| `get_cluster_health`     | 지정 클러스터 상태·파티션 건강 상태 조회       |
| `list_topics`            | 지정 클러스터의 토픽 목록 조회             |
| `list_consumer_groups`   | 지정 클러스터의 Consumer Group 목록 조회 |
| `get_consumer_group_lag` | 지정 그룹의 파티션별 Lag·Offset 조회     |
| `list_cluster_events`    | 지정 클러스터의 이벤트 조회               |

공통 규칙:

* 대상 클러스터가 필요한 도구는 `cluster_id` 필수.
* 그룹별 도구는 `group_name`도 필수.
* 입력 누락 시 기본 클러스터로 대체하지 않는다.
* 경로 인자를 안전하게 인코딩한다.
* 도구별 설명·입력·출력 JSON Schema를 정의한다.
* read-only annotation을 설정하되 실제 권한 검사 수단으로 취급하지 않는다.
* API가 지원하는 필터·페이지 방식만 사용한다.
* 결과 개수·응답 크기에 상한을 둔다.
* 잘린 결과는 `truncated` 등으로 표시하고 전체 결과인 것처럼 반환하지 않는다.
* 백엔드가 전체 목록만 반환하는 경우 전송 크기 제한과 MCP 출력 제한을 구분한다.
* Kafka 메시지 본문·SCRAM 비밀번호·인증 설정은 공개하지 않는다.
* 기존 백엔드가 매 호출의 최종 권한을 판단하게 한다.

대응 API가 없거나 필요한 권한 통제가 확인되지 않는 도구는 임의 우회하지 않는다. 안전한 범위만 구현하고 구체적인 차단 사유와 필요한 백엔드 개선을 기록한다.

## 7. 결과와 오류 처리

SDK의 표준 기능을 활용해 구조화된 결과와 호환용 텍스트를 반환한다.

필요한 결과 정보:

* 대상 클러스터
* 조회 데이터
* 조회 시각
* 원본 관측 시각: 백엔드가 제공하는 경우만
* 데이터 출처·신선도: 확인 가능한 경우만
* 부분 실패·잘림·기타 제한

조회 시각을 원본 데이터의 관측 시각으로 표시하지 않는다.

HTTP 200만 보고 업무 성공 또는 정상 상태로 판단하지 않는다. 응답 본문에 조회 실패·권한 부족·미지원 상태가 있으면 의미를 보존한다.

* 조회 실패를 정상·0건·Lag 0으로 바꾸지 않는다.
* MCP 프로토콜 오류와 도구 실행 오류를 구분한다.
* 인증 만료·접근 거부·대상 없음·요청 제한·timeout·백엔드 장애를 구분한다.
* 복수 API를 조합하면 부분 성공과 전체 실패를 구분한다.
* 오류 본문과 내부 정보를 무제한 노출하지 않는다.
* 측정값과 기존 판정 결과를 반환하고 원인을 임의 추론하지 않는다.
* 이벤트 설명 등 외부 문자열은 데이터로 취급한다.

## 8. REST Client와 로그

* 공통 HTTP Client와 timeout·취소를 구현한다.
* 동시 호출 수·응답 바이트 수를 제한한다.
* 401·403을 자동 재시도하지 않는다.
* 필요한 재시도는 조회의 일시적 오류에만 제한적으로 적용한다.
* 구조화 로그에 도구명·클러스터·처리 시간·결과 코드를 기록한다.
* 토큰·Authorization 헤더·전체 요청 및 응답 본문은 기록하지 않는다.
* MCP 실행 로그와 기존 서비스 감사 기록의 범위를 문서에서 구분한다.
* 이번 단계에서는 별도 DB·공유 캐시·백그라운드 수집기를 추가하지 않는다.

## 9. 테스트와 검증

실제 운영 서비스 없이 검증하도록 `httptest` 기반 mock REST 서버를 사용한다. 테스트 데이터는 분석한 실제 DTO에 맞춘 합성 데이터로 작성한다.

필수 검증:

* 정상 REST 응답의 MCP 결과 변환
* `cluster_id` 누락 거부와 대상 API 경로 일치
* Bearer 인증 전달과 토큰 비노출
* 401·403·404·429·5xx 처리
* HTTP 200 본문에 담긴 업무 실패 상태 보존
* timeout·취소·비정상 JSON·응답 크기 초과
* 부분 실패와 목록 잘림 표시
* 특수문자 경로 인코딩
* 리다이렉트에 의한 토큰 외부 전달 차단

SDK MCP Client를 사용해 실제 stdio 프로세스와 연결하고 다음을 통합 검증한다.

초기화 → 도구 목록 조회 → 도구 호출 → 종료

stdout에 로그가 섞이지 않는지도 확인한다.

다음을 실행한다.

* `go test ./...`
* `go vet ./...`
* `go build ./cmd/ableops-kafka-mcp`

환경 문제로 실행하지 못한 항목은 원인과 함께 보고한다. mock 통과를 실제 백엔드 연동 성공으로 표현하지 않는다.

* API 계약 확인과 테스트 규칙

설정 예시에 실제 자격증명을 넣지 않는다. 특정 클라이언트의 환경변수 치환 문법을 확인 없이 가정하지 않는다.

## 11. 진행 및 완료 보고

초기 분석 후 핵심 API 계약과 구현 계획을 짧게 정리하고 바로 구현을 진행한다. 일반적인 구현 선택은 합리적으로 결정하고 반복 확인을 요청하지 않는다.

완료 기준:

* 신규 프로젝트가 기존 소스와 독립적으로 빌드된다.
* MCP Client가 도구 목록을 조회하고 mock 백엔드에 대해 호출할 수 있다.
* 문서의 PowerShell 명령으로 재현할 수 있다.
* 인증·클러스터 범위·오류 상태가 보존된다.
* 기존 `kadmin` 작업본이 변경되지 않는다.

최종 보고에는 다음을 간결하게 포함한다.

1. 구현된 기능과 주요 파일
2. 빌드·실행·클라이언트 연결 방법
3. 테스트 결과와 미실행 항목
4. 실제 백엔드 연동 검증 여부
5. 기존 소스 변경 여부
6. 공용 MCP 서비스와 채팅 연동을 위한 후속 작업
