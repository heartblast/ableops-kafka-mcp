# 실제 Backend 연동 검증 및 Streamable HTTP·사용자별 인증 구현

너는 Go 백엔드 엔지니어다. 기존 `ableops-kafka-mcp`에 **실제 Backend 연동 검증과 Streamable HTTP·사용자별 인증**을 구현하라. 계획만 제시하지 말고 코드·테스트·실행 문서를 완성하라.

## 1. 환경과 목표

* MCP 프로젝트: `D:\golang\go-workspace\ableops-kafka-mcp`
* Backend 소스: `D:\golang\go-workspace\kadmin`
* Backend 주소: `http://localhost:8080`
* 환경: Windows / PowerShell
* Backend는 사용자가 직접 실행한다. 임의로 시작·종료·재시작하지 않는다.
* 기존 구현: 공식 Go SDK 기반 stdio 서버와 조회 도구 6개. 실제 코드에서 구현 상태를 확인한다.

이번 목표:

1. 기존 도구의 실제 Backend 연동 확인
2. 기존 stdio를 유지하면서 Streamable HTTP 추가
3. HTTP 호출자의 신원과 Backend 사용자 권한 연결
4. 사용자 간 데이터·자격증명 격리 및 운영 기반 구축

채팅·LLM·조회 도구 추가·변경 신청·승인·반영은 제외한다.

## 2. 진행 원칙

* 적용 지침과 두 저장소의 Git 상태를 확인하고 기존 변경을 보존한다.
* 필요한 MCP 초기화·REST Client·설정·테스트와 Backend 인증·권한 코드만 읽는다.
* 독립적인 검색·읽기는 묶고, 확인한 계약은 재사용한다.
* 먼저 현재 구조와 인증 선택을 짧게 정리한 뒤 구현한다.
* 개발 중 관련 패키지만 검증하고 마지막에 전체 테스트·vet·빌드를 수행한다.
* 일반적인 구현 선택은 직접 결정한다. 무관한 리팩터링·의존성 일괄 업그레이드·반복 전체 분석을 하지 않는다.
* push·배포·운영 데이터 변경은 수행하지 않는다.

Backend 소스는 기본적으로 참조용이다. **이번 인증 연계에 꼭 필요한 최소 변경만 허용**하며, 별도 diff·테스트로 구분한다. 기존 로그인·세션·RBAC 동작을 유지한다. DB 변경은 가능한 한 피하고, 실제 DB 마이그레이션은 자동 실행하지 않는다.

## 3. 실제 연동 검증부터 수행

`http://localhost:8080`의 연결·상태를 확인한 후 기존 여섯 도구를 검증한다.

* `list_clusters`
* `get_cluster_health`
* `list_topics`
* `list_consumer_groups`
* `get_consumer_group_lag`
* `list_cluster_events`

테스트용 사용자 토큰과 대상 ID는 환경변수 등 기존 안전한 설정 경로로 주입받는다. 실제 값을 출력·저장소 커밋하지 않는다. 기본 관리자 비밀번호 추측, 설정 파일에서 비밀값 수집, 무단 테스트 계정 생성은 하지 않는다.

검증 내용:

* 실제 JSON과 DTO·MCP 출력의 일치
* 클러스터·그룹·이벤트의 대상 범위 유지
* 관측 시각·스냅샷·부분 실패·빈 결과 구분
* 접근 불가 클러스터, 만료/무효 토큰, 없는 대상 처리
* HTTP 200 본문에 담긴 업무 실패 보존

읽기 전용 요청만 수행한다. 데이터가 없으면 정상적인 빈 결과로 처리하고 임의로 생성하지 않는다.

Backend가 미실행이거나 토큰이 없으면 mock·코드 구현을 계속하고, 실연동만 미검증으로 남긴다. 필요한 설정은 마지막에 한 번에 안내한다. 무효 토큰 테스트를 실제 만료 테스트로, mock 권한 테스트를 실환경 권한 검증으로 표현하지 않는다.

## 4. Streamable HTTP 추가

공식 SDK의 현재 고정 버전과 지원 API를 확인하여 기존 도구 등록 로직을 재사용한다.

* `--transport=stdio|http`, 기본 `stdio`
* HTTP 기본 주소: `127.0.0.1:8081`
* MCP 엔드포인트: `/mcp`
* `/healthz`, `/readyz`: 민감정보 없는 상태 응답
* 기존 Backend의 8080 포트와 충돌하지 않게 한다.
* 프로토콜 초기화·버전 협상·요청·응답은 SDK에 맡긴다.
* 종료 신호, 진행 중 요청 취소, 정상 종료를 처리한다.
* 요청 크기·동시 호출·처리 시간·유휴 연결을 제한한다.
* 스트리밍과 충돌하는 일괄 응답 timeout이나 프록시 버퍼링을 피한다.
* Origin 검증을 구현하고 브라우저 접근 허용목록은 명시적으로 설정한다. Origin 부재를 인증으로 취급하지 않는다.
* 로컬 HTTP와 사내 HTTPS 배포 설정을 구분한다.
* 기존 stdio stdout 프로토콜과 stderr 로그 동작을 유지한다.

가능하면 SDK의 stateless 모드를 사용해 세션 상태를 줄인다. 세션을 사용한다면 인증 주체에 바인딩하고, 세션 ID를 인증 수단으로 사용하지 않는다.

## 5. 사용자별 인증 설계와 구현

**HTTP 모드에서 프로세스 공용 Backend 토큰을 모든 사용자에게 적용하지 않는다.**

먼저 기존 인증 구조와 사용 가능한 인증 서버를 확인하고 다음 원칙에 따라 최소 구현을 선택하라.

* MCP용 액세스 토큰의 발급·검증 경로를 분명히 한다.
* Backend용 자격증명은 별도 사용자 위임 경로로 연결한다.
* MCP와 Backend의 토큰 audience를 구분한다.
* MCP용 토큰의 단순 Backend 전달은 금지한다.
* 임의 `user_id`, `X-User` 헤더 등으로 사용자 신원을 신뢰하지 않는다.
* 기존 관리자 공용 계정으로 대신 실행하지 않는다.
* Backend의 현재 사용자·클러스터 권한을 최종 적용한다.

사내 OAuth 서버를 사용할 수 있으면 공식 MCP 인증 규격과 SDK에 맞춰 연계한다. discovery·protected resource metadata·토큰 검증·scope·만료 처리를 구현하고, 필요한 Backend 위임 토큰 연계를 최소 변경으로 추가한다. 직접 암호 프로토콜을 설계하지 않는다.

**인증 서버가 제공되지 않은 경우에도 구현을 멈추지 않는다.** 다음의 제한된 로컬 검증 모드를 제공한다.

* 사용자별 별도 MCP 접근 토큰과 각 사용자의 Backend 세션 토큰을 서버 측에서 안전하게 매핑한다.
* MCP 토큰은 암호학적으로 안전한 난수로 발급하고 해시로 검증한다.
* Backend 토큰은 응답·로그에 노출하지 않는다.
* 만료·폐기와 사용자 매핑 검증을 제공한다.
* 등록은 로컬 관리자용 절차로 제한하고 공개 등록 API를 만들지 않는다.
* 비밀 설정은 Git에서 제외하고 안전한 파일 권한을 안내한다.
* 이 방식은 OAuth 표준 연동이 아닌 개발용 인증이며, 임의 Bearer 설정이 가능한 클라이언트에 한정됨을 명시한다.
* 기본 loopback 바인딩을 강제하고 공용 서비스 인증 완료로 보고하지 않는다.
* 추후 OAuth로 교체할 수 있도록 인증과 Backend 자격증명 해석만 분리한다.

각 HTTP 요청마다 인증과 유효기간을 검사한다. 권한 회수·로그아웃·Backend 세션 만료를 오래된 캐시로 우회하지 않는다. 공유 REST Client의 토큰 필드를 요청마다 덮어쓰지 말고 요청별 자격증명을 전달한다. 서로 다른 사용자의 동시 호출이 섞이지 않게 한다.

## 6. 운영·추적

* 요청 추적 ID로 MCP 도구 호출과 Backend 요청을 연결한다.
* 사용자 식별자, 클라이언트 식별자(검증 가능한 경우), 도구, 클러스터, 처리 시간, 결과 코드를 기록한다.
* 토큰·Authorization·전체 요청/응답 본문은 기록하지 않는다.
* 인증 실패·Backend 인증 만료·권한 거부·Backend 장애를 구분한다.
* 호출 제한은 전체와 사용자별로 적용한다.
* 읽기 전용 도구만 노출한다.
* MCP 실행 로그와 Backend 감사 기록의 범위를 구분한다.

## 7. 검증

기존 테스트를 재사용하고 다음을 추가한다.

1. 기존 stdio 회귀와 여섯 도구 호출
2. SDK Client를 통한 실제 HTTP 초기화·도구 목록·호출·종료
3. 무인증·잘못된 토큰·만료·폐기된 토큰 거부
4. 서로 다른 권한의 사용자 A/B 동시 호출과 자격증명 격리
5. 허용되지 않은 클러스터 접근 차단
6. 세션 사용 시 다른 사용자의 세션 재사용 차단
7. Backend 401/403·timeout·부분 실패 보존
8. Origin·요청 크기·호출 제한·정상 종료
9. 토큰·민감 응답의 로그 비노출
10. 선택한 인증 방식의 핵심 검증: OAuth면 issuer/audience/scope, 로컬 모드면 토큰 매핑·만료·loopback 강제

실연동 테스트는 명시적 실행 옵션으로 분리하고, 기본 테스트와 CI는 운영 Backend에 의존하지 않게 한다. 테스트 계정·토큰이 부족한 실제 시나리오는 mock 검증과 구분한다.

최종 검증:

* `go test ./...`
* `go vet ./...`
* `go build ./cmd/ableops-kafka-mcp`
* 환경이 지원하면 인증·동시성 관련 패키지에 `go test -race`

Backend를 수정했다면 영향 패키지도 검증한다. 실행 중인 Backend가 이전 바이너리면 재시작 필요를 명시하고 신규 인증 경로를 실검증했다고 보고하지 않는다.

## 8. 산출물과 보고

기존 문서를 갱신하고 중복 문서를 늘리지 않는다.

* stdio/HTTP 설정과 PowerShell 실행 예시
* localhost:8080 Backend 연동 검증 스크립트
* 실제 값 없는 인증·설정 예제
* API 매핑과 실제 검증 결과
* 선택한 인증 구조, 제약, OAuth 전환에 남은 작업
* 사내 HTTPS 배포·프록시 설정 안내
* 사용자별 인증 등록·만료·폐기 절차
* Backend 변경 사항과 재시작 필요 여부

완료 시 **구현 범위, 인증 방식, 실행 명령, 자동 테스트, 실제 연동 결과, 미검증 항목**을 간결히 보고하라. 특히 로컬 검증 완료와 다중 사용자 공용 배포 준비 완료를 명확히 구분하라.
