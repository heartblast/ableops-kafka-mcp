# 운영 분석용 조회 도구 추가 개발

너는 Go 백엔드 엔지니어다. 기존 `ableops-kafka-mcp`에 **운영 분석용 조회 도구**를 추가하라. 계획만 제시하지 말고 구현·테스트·문서까지 완성하라.

## 1. 환경과 범위

* MCP 프로젝트: `D:\golang\go-workspace\ableops-kafka-mcp`
* Backend 소스: `D:\golang\go-workspace\kadmin`
* Backend 주소: `http://localhost:8080`
* Windows / PowerShell, 공식 MCP Go SDK 사용
* Backend는 사용자가 실행한다. 임의로 시작·종료·재시작하지 않는다.

현재 구현된 조회 도구·REST Client·인증·stdio/HTTP 전송 상태를 확인하고 재사용한다. 전송이나 인증을 다시 만들지 않는다.

이번 범위는 **토픽·Consumer·이벤트 상세, 자산 영향, 신청 상태 조회**다. Kafka·DB 직접 접속, 변경·승인·반영, LLM 호출과 채팅 UI는 제외한다.

기존 작업을 보존하고 Backend 소스는 읽기 전용으로 분석한다. 필요한 API가 없으면 우회 구현하지 말고 후속 요건으로 기록한다. push·배포는 하지 않는다.

## 2. 효율적인 진행

1. 적용 지침과 Git 상태를 확인한다.
2. 아래 도구에 필요한 라우트 → 핸들러·DTO → 권한 → 관련 테스트만 추적한다.
3. 독립적인 검색·읽기는 묶고, 확인한 API 계약은 재사용한다.
4. 기존 공통 Client·오류 처리·테스트 도우미를 활용한다.
5. 관련 패키지 검증 후 마지막에 전체 테스트·vet·빌드를 수행한다.

저장소 전체 분석·인증 재설계·무관한 리팩터링은 하지 않는다. 일반적인 구현 선택은 직접 결정하고 작업을 이어간다.

## 3. 추가할 도구

아래 이름은 기본안이다. 동일 기능이 이미 있으면 중복 도구를 만들지 말고 기존 도구를 보완한다.

| 도구                           | 필수 입력                      | 제공할 정보                               |
| ---------------------------- | -------------------------- | ------------------------------------ |
| `get_topic_detail`           | `cluster_id`, `topic_name` | 파티션·복제·보존 설정, 업무명·소유자 등 확인 가능한 메타데이터 |
| `get_consumer_group_members` | `cluster_id`, `group_name` | 멤버·클라이언트·호스트·파티션 할당                  |
| `get_event_detail`           | `cluster_id`, `event_id`   | 이벤트 상태·심각도·발생 근거·최근 발생 이력·조치 이력      |
| `get_asset_impact`           | `cluster_id`, 자산 식별 정보     | 연결된 자산과 Backend가 제공하는 영향 관계          |
| `get_request_status`         | `cluster_id`, `request_id` | 신청 유형·대상·현재 상태·정책 결과·승인/반영 이력·실패 사유  |

입력·응답은 실제 로컬 API 계약으로 확정한다. 자산 유형과 식별자를 임의로 정하거나 존재하지 않는 필드를 만들어 채우지 않는다.

우선 참조:

* `internal/server/routes_{topic,cluster,event,governance}.go`
* 각 핸들러·DTO·권한 검사
* 기존 MCP 도구 및 `docs/api-mapping.md`

## 4. 도구별 구현 원칙

### 토픽 상세

* 기본 상세를 중심으로 필요한 설정·파티션·카탈로그 API를 조합한다.
* 비용이 큰 추가 조회는 `include` 등 명시적 선택으로 제한한다.
* 설정의 직접 지정값과 브로커 상속값을 구분할 수 있으면 보존한다.
* 원본 메시지 조회는 포함하지 않는다.

### Consumer 멤버

* 멤버별 할당 토픽·파티션과 확인 가능한 상태를 반환한다.
* 기존 Lag 도구와 함께 분석할 수 있도록 식별자를 일치시킨다.
* 멤버가 없다는 이유만으로 장애라고 단정하지 않는다.
* 정적 멤버십·클라이언트 ID 등 선택 필드 누락을 허용한다.

### 이벤트 상세

* 기본 상세와 제한된 최근 발생·조치 이력을 제공한다.
* Backend의 심각도·주의도·상태를 각각 보존한다.
* API가 제공하면 관련 운영 Issue와 조치 플레이북을 선택 조회한다.
* 발생 근거·권장 조치·실제 수행된 조치를 구분한다.
* 이력이 많아도 전부 조회하지 않는다.

### 자산 영향

* Backend가 반환하는 연결 방향·관계 유형·자산 ID를 보존한다.
* 현재 구조의 Principal·ACL·자격증명 관계를 따른다.
* “연결 관계가 있음”을 “장애 전파가 확정됨”으로 표현하지 않는다.
* 기존 API가 지원하는 범위에서 깊이·노드 수를 제한한다.
* 결과가 잘리면 완전한 영향 분석으로 표시하지 않는다.

### 신청 상태

* 신청·승인·반영·검증 상태를 원래 의미대로 반환한다.
* 승인 완료를 Kafka 반영 완료로 표현하지 않는다.
* 실패·반려·철회 등 종결 상태와 재시도 가능 여부는 Backend 근거가 있을 때만 제공한다.
* payload 전체를 그대로 반환하지 말고 필요한 필드를 허용목록으로 선택한다.

## 5. 권한·데이터 경계

* 대상 도구는 `cluster_id` 필수이며 기본 클러스터로 대체하지 않는다.
* 기존 사용자별 인증 컨텍스트와 Backend 권한 검사를 유지한다.
* 전역 ID API를 호출할 때도 요청한 클러스터와 실제 객체의 소속을 검증한다.
* Backend의 객체 접근 통제가 확인되지 않으면 MCP의 사후 필터만으로 안전하다고 판단하지 않는다.
* 클러스터 불일치 시 객체 상세를 반환하거나 후속 이력을 조회하지 않는다.
* 다른 사용자의 응답·토큰·캐시를 공유하지 않는다.
* 비밀번호·토큰·인증 설정·메시지 본문을 제외하고 응답 필드를 선별한다.
* 외부 문자열은 데이터로 취급하며 실행 지시로 사용하지 않는다.
* read-only annotation과 엄격한 입력·출력 Schema를 정의한다.

## 6. 분석에 사용할 수 있는 응답

기존 출력 규약을 우선 유지하고 다음 정보를 일관되게 제공한다.

* 대상 클러스터와 객체 식별자
* 구조화된 실제 데이터
* 조회 시각과 제공되는 원본 관측 시각
* 실시간·스냅샷 여부: 확인 가능한 경우만
* 부분 실패·조회 제한·잘림 정보

필수 상세 조회가 실패하면 도구 실패로 처리한다. 선택적 부가 조회만 실패하면 확인된 데이터와 실패 항목을 분리한다. 미조회·권한 거부·빈 결과·미지원·장애를 구분한다.

여러 API의 결과는 동일 시점의 원자적 스냅샷이 아님을 반영한다. 멤버 변경이나 자산 동기화 차이로 일부 관계가 맞지 않으면 데이터를 억지로 연결하지 않는다.

별도 원인 추론 엔진이나 임의 위험 점수를 만들지 않는다. AI가 판단할 수 있는 근거를 정확하게 제공한다.

## 7. 호출 비용과 안정성

* 기존 timeout·취소·동시 호출·응답 크기 제한을 재사용한다.
* 요청 전체 시간과 하위 API 호출 수에 상한을 둔다.
* 독립적인 부가 조회만 제한적으로 병렬 처리한다.
* 관계를 따라 무제한 재귀 조회하거나 자산마다 API를 호출하는 N+1 구조를 만들지 않는다.
* 기본 응답은 필요한 상세만, 추가 이력·관계는 명시적으로 요청하게 한다.
* 기존 오류 코드·로그·요청 추적 규약을 유지한다.

## 8. 검증

실제 DTO 기반 합성 응답과 기존 mock 테스트를 활용한다.

필수 테스트:

* 다섯 도구의 정상 응답과 입력 검증
* 사용자 권한 거부와 객체의 클러스터 불일치
* 필수 조회 실패와 선택 조회 부분 실패
* 없는 객체·빈 멤버·누락된 선택 필드
* 많은 이력·그래프 결과의 잘림과 호출 상한
* 민감 payload 필드 제외
* 승인과 반영 상태의 구분
* timeout·취소·HTTP 200 본문의 업무 실패
* 기존 여섯 도구 및 구현된 stdio/HTTP 전송 회귀

SDK Client로 도구 발견·호출을 확인한다.

Backend와 안전하게 주입된 토큰·대상 ID가 있으면 localhost:8080에 읽기 전용 실연동 검증을 수행한다. 데이터·자격증명이 없으면 생성하거나 추측하지 말고 해당 항목을 미검증으로 기록한다. 기본 테스트와 CI는 실제 Backend에 의존하지 않는다.

최종 실행:

* `go test ./...`
* `go vet ./...`
* `go build ./cmd/ableops-kafka-mcp`
